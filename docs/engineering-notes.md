# Relay engineering notes

The running engineering log for the project: design decisions, bugs found and how they were fixed, and known limitations in full detail. The short, user-facing README is [../README.md](../README.md). Paths below are relative to the repository root.

---


A grounded AI assistant over your own Google Workspace — Drive/Docs, Gmail, Calendar, and Sheets indexed into a RAG pipeline you can ask natural-language questions against, every answer cited back to its real source or refused rather than guessed.

Full spec: [PRD.md](../PRD.md). Current status: **M1, M2, and M5 complete, M3 done for both push-capable surfaces** — OAuth, Drive/Docs+PDF ingestion (with real chunking), Gmail ingestion + polling, Calendar ingestion + push sync, Sheets ingestion (structured, per-row facts riding on Drive's own push channel), the chat pipeline, background job processing, a unified auto-sync toggle covering every mechanism, a 23-question ground-truth + 7-case adversarial eval suite spanning all four surfaces, and an observability dashboard (FR-20: query volume, refusal rate, per-surface sync lag, latency) are implemented and verified against real Google/QStash infrastructure with real personal data. The Apps Script companion (M4) is the only milestone still ahead (see PRD §9).

## Why this exists

Built specifically to close a gap found while tailoring resumes against real job postings: hands-on Google Workspace integration, named down to the API level in one posting, was the single most recurring missing skill across ~20 applications. See PRD §1.

## Why hand-rolled OAuth

The OAuth2 authorization-code + PKCE flow (`lib/google/oauth.ts`, `lib/crypto.ts`) is written against Google's raw endpoints directly, not through `google-auth-library`'s `OAuth2Client.generateAuthUrl()`/`.getToken()` convenience methods. That's deliberate — the whole point of this project is proving this flow is understood and can be written by hand, not delegated to a library or (elsewhere in this portfolio) to n8n's Google nodes. See PRD §6.3.

The `googleapis` SDK is still used in `lib/google/client.ts` to actually call the Drive/Docs/Gmail/Calendar/Sheets APIs once an access token is already held — that's just a typed API client, it doesn't hide any OAuth mechanics, so using it there isn't a contradiction.

## Stack

Next.js (App Router) · Drizzle ORM + Postgres · Qdrant (vector store) · Hugging Face Inference API (embeddings + reranking) · Groq (generation) — same core stack as this portfolio's Mimo project, reused deliberately rather than introducing new infra alongside a new integration surface.

## Setup

Local infrastructure (Postgres, Qdrant, encryption/state secrets) is already
provisioned — dedicated `relay-postgres` and `relay-qdrant` Docker containers
(their own volumes, not shared with any other project on this machine), with
a fresh AES-256-GCM key, HMAC state secret, and Qdrant API key generated
straight into `.env.local`. What's left needs your own accounts in a browser:

```bash
./scripts/setup.sh
```

This walks you through, in order:

1. **Google Cloud** — create a project, enable the Drive/Docs/Gmail/Calendar/Sheets APIs.
2. **Google Cloud** — configure the OAuth consent screen (External, Testing mode, the exact 5 scopes `lib/google/scopes.ts` requests, and your own account added as a test user).
3. **Google Cloud** — create the OAuth Client ID and capture `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`.
4. **Hugging Face** — an Inference API token (embeddings + reranking).
5. **Groq** — an API key (generation).

Every value it captures is written straight to `.env.local` (already
gitignored — see `.gitignore`). Because this stays in Google's Testing
publishing status (deliberate, see PRD §6.4/§8), you'll hit an "unverified
app" warning on first connect — click through it, it's expected for an app
only you are a test user of.

Background jobs (ingestion) run through a local QStash emulator when `QSTASH_DEV=true` (see `.env.example`) — `instrumentation.ts` tries to auto-start it itself, but its auto-installer has a confirmed bug on Windows/Git Bash (`tar` misreads a `C:\...` path as a remote-host spec and fails to extract). On Windows, start it manually first, in its own terminal, and leave it running:
```bash
npx @upstash/qstash-cli@latest dev
```

Then, in another terminal:
```bash
npm install
npm run db:push
npm run dev
```

Open `http://localhost:3000/connections`, connect Drive, click **Sync Drive/Docs now**, then ask a question at `http://localhost:3000/chat`. (`/` is now the public site — see below.)

No accounts to click through, or setting up on a machine without the local
Postgres/Qdrant already running? See `.env.example` for every variable this
app reads and where it comes from — `scripts/setup.sh` is a convenience, not
the only way to fill it in.

## Architecture

```
Browser → Next.js (App Router pages + API routes)
        → hand-rolled OAuth2/PKCE against Google's raw endpoints (lib/google/oauth.ts)
        → googleapis SDK for Drive/Docs/Gmail/Calendar/Sheets calls (lib/google/client.ts)
        → Drizzle → Postgres (provenance, connections, chat, observability)
        → Qdrant (vectors) + Hugging Face (embed/rerank) + Groq (generation)
```

See [PRD.md §6](../PRD.md#6-proposed-architecture) for the full component breakdown, request flow, and the reasoning behind each non-obvious choice (why not n8n, why Gmail polls instead of pushing, why v1 has no public demo).

## Known limitations (M1)

- The Qdrant client connects over plain `http://localhost` with an API key — Qdrant itself warns about this ("Api key is used with unsecure connection"). Acceptable for local dev where the traffic never leaves the machine; a real deployment needs TLS in front of Qdrant (e.g. a reverse proxy) so the key isn't sent in the clear even on the wire between app and DB.
- The access-token cache in `lib/google/tokens.ts` is in-process, so it only single-flights within one server instance — not a correctness issue at this project's scale, just not shared across serverless instances (see its own inline comment).
- Sheets rows have a positional, not content-based, `sourceId` (`spreadsheetId:tab:rowIndex`) — deleting a row shifts every later row up by one, so `persistChunk` correctly re-embeds the shifted content under its new position's old sourceId, but the sheet's true last row's old slot becomes an orphan until something else touches it, and a citation can briefly point at a shifted row rather than the one originally cited. Documented in `lib/ingest/sheets.ts`, not discovered later — there's no reliable stable key across arbitrary spreadsheets to do better here for v1.
- Calendar's backfill window defaults to -90/+180 days from now (`lib/ingest/calendar.ts`'s `DEFAULT_PAST_DAYS`/`DEFAULT_FUTURE_DAYS`) — Calendar has no cheap equivalent of Drive's `getStartPageToken()`, so bounding the window keeps a long-lived calendar's history of recurring-meeting instances from meaning years of events get ingested. Deliberate default, not a hard limit.
- Calendar's incremental sync (via `syncToken`) is **not** bounded to that same window once established — Google's own API rejects combining `timeMin`/`timeMax` with a `syncToken` on later calls, so once the watermark exists, ongoing sync tracks changes across the whole calendar, not just the original backfill range. Confirmed from Google's own docs, not assumed; a new event created far outside the original window still gets caught by an ongoing sync, which is the right behavior even though it's asymmetric with the bounded initial import.
- Cancelled/deleted Calendar events (and deleted Drive files, deleted Gmail messages) don't retract their already-ingested chunks — the adapters correctly *stop* re-ingesting them, but nothing proactively deletes what's already in Postgres/Qdrant. Consistent, pre-existing v1 limitation across all three surfaces, not something newly introduced for Calendar.
- Gmail's `history.list` polling only honors the `labelId` half of a configured scope, not the date range — a "before" bound only ever meant "stop the initial backfill there," since an ongoing poll is inherently forward-looking and `history.list` has no date filter at all. Documented in `lib/ingest/gmail.ts`, not a silent gap.
- Gmail freshness is 5-minute polling, not real push notifications — deliberate for now (PRD §6/§11: a Pub/Sub topic would force a future user through GCP project setup just to connect Gmail). Revisit once this is actually deployed to a real public HTTPS URL: real Gmail push notifications (`users.watch()` + Google Cloud Pub/Sub) become genuinely viable at that point, either push-subscription (needs the same public URL Drive's `changes.watch` needs) or pull-subscription (no public URL needed, app polls Pub/Sub instead of Gmail directly — near-instant without hitting Gmail's own per-user quota). Pub/Sub's free tier (10 GB/month throughput) comfortably covers a single real inbox's notification volume, though GCP still requires a billing account linked to enable the API at all. Explicitly deferred rather than built now, since there's no public URL yet to verify a real push end-to-end against.
- A full Gmail re-backfill still re-fetches every message (`messages.get`) to check its content hash, even when nothing changed — the hash check only skips the expensive re-embed step, not the Gmail API call itself. Confirmed in practice: re-running backfill on an unchanged ~211-message inbox still took a few minutes. Fine at this project's scale; a real optimization would check `messages.list`'s own cheap metadata (or just the historyId delta) before ever calling `messages.get`.
- **`googleConnections.autoSyncEnabled`** is the one unified "keep this connection fresh automatically" switch, covering both mechanisms transparently: ON registers Drive's push channel (via its own initial backfill) and flags this connection for Gmail's polling job; OFF genuinely stops Drive's channel with Google (`channels.stop`) rather than just ignoring future notifications, and the polling job (`app/api/jobs/gmail-sync/route.ts`) filters on this flag via a join, not just "does a scope exist." Verified live: toggled on (both surfaces started syncing immediately, confirmed via the polling status from earlier), toggled off (flag flips, a manually-triggered poll afterward confirmed zero rows processed — `lastSyncedAt` genuinely unchanged, not just "nothing new to sync"). Manual "Sync now" clicks work regardless of this flag either way — it only gates the *automatic* paths.
- ~~Calendar ingestion is an interface stub~~ — `lib/ingest/calendar.ts` implements FR-7 (backfill via `events.list`, `singleEvents: true` so recurring meetings expand into individually citable occurrences) and gets real push notifications via `events.watch` (FR-10) — the same mechanism as Drive, no Pub/Sub needed, unlike Gmail. `lib/google/watch.ts`'s renewal-lookup was generalized from Drive-only to any surface (`findChannelsDueForRenewal(surface)`) and the renewal worker renamed from `renew-drive-watch` to `renew-watch-channels` to cover both. The auto-sync toggle and connections UI were extended to include Calendar alongside Drive/Gmail. Verified against this author's real Google Calendar end-to-end: backfilled a real event (an actual job-interview booking), got a correctly cited answer to "what is my Pivotly screening about and when" pointing at Calendar's own real `htmlLink`, registered a genuine `events.watch` channel through a temporary tunnel with the correct ~24h expiration, forced it near-expiry and confirmed the generalized renewal job replaced it, then stopped the real channel and reverted the tunnel-only env changes when done. Chunk counts matched exactly between Postgres and Qdrant throughout (3622/3622 after the Calendar backfill).
- Gmail backfill/sync is sequential per-message (one `messages.get` + one embed call at a time) — confirmed in practice against a real, active inbox: 211 messages over about a week's date range took roughly 5 minutes end to end through the QStash job. Fine at this project's real personal-inbox scale; a much larger backfill would want batching/parallelism.
- ~~Sheets ingestion is an interface stub~~ — `lib/ingest/sheets.ts` implements FR-8 (one `IngestedChunk` per row, header cells supplying field labels, so "Name: John Doe, Status: Active" reads as a real fact rather than a floating fragment) and FR-12 (no channel of its own — `app/api/jobs/drive-sync/route.ts` triggers Sheets' own independent `syncChanges` after handling Drive's own sync, only once Sheets has been backfilled at least once). Verified against this author's real Drive: backfilled 4 real spreadsheets (4153 rows total, one with over 3,000), asked a structured question spanning multiple rows ("what information does the Pipeline Runs spreadsheet track") and got a correctly synthesized, multi-row-cited answer with real range-anchored citation URLs, then directly triggered the `drive-sync` job and confirmed it really did cascade into establishing Sheets' own sync watermark as a side effect — proving the FR-12 coupling works, not just that it compiles. Chunk counts matched exactly throughout (7775/7775). One genuinely surprising finding, confirmed rather than assumed: none of this needed the dedicated `spreadsheets.readonly` scope at all — `drive.readonly` alone was sufficient for the Sheets API's own read calls in practice, the same way it already was for reading Docs content. The separate scope stays requested (`lib/google/scopes.ts`) for FR-2's least-privilege intent and explicit-consent clarity, not because it turned out to be technically required.
- `instrumentation.ts`'s automatic QStash dev-server startup doesn't work on Windows/Git Bash — confirmed bug, not a maybe: the SDK shells out to `tar` with a raw `C:\...` path, and `tar` interprets the drive letter + colon as a remote-host spec (`host:path` syntax) and fails to extract. Works fine as documented for a real deployment (`QSTASH_DEV` unset) and should work on Linux/Mac for local dev; on Windows, run `npx @upstash/qstash-cli@latest dev` manually first (see Setup above) rather than relying on the auto-start.

**Fixed since first written:**
- **A real bug, not a hypothetical one:** that ~5-minute Gmail backfill got delivered twice by QStash — the request log showed two separate "POST /api/jobs/backfill 200 in 5.0min" completions back to back, almost certainly QStash retrying after its own delivery timeout while the first attempt was still genuinely in progress server-side. Both ran the same backfill concurrently, doubling the real Gmail API call rate, and tripped Gmail's own "Units per minute per user" quota — surfaced as a real `last_error` on the connections page, not just a theoretical risk. First fixed with an in-process dedup guard, then upgraded to a durable one (`lib/sync-lock.ts`, backed by `surface_sync.sync_started_at`) once it became clear the same signal was needed for the connections UI anyway — see the next entry. `claimSyncLock`/`releaseSyncLock` are used by all three ingestion job handlers (`backfill`, `drive-sync`, `gmail-sync`), not just the one that originally broke. Also added 429 retry-with-backoff around every Gmail API call in `lib/ingest/gmail.ts` as defense in depth, independent of the dedup fix. Verified for real afterward: triggered a fresh sync through a temporary ngrok tunnel, confirmed a single clean execution (not a pair), the error cleared, and — as a bonus — real new mail had arrived during testing, so this also ended up being the first live proof that the `history.list` incremental "new message" path (not just the initial cursor-establishment call) actually works, catching and correctly ingesting 5 genuinely new messages.
- **The connections UI showed no sync-in-progress state at all** — the backfill/sync request returns a 202 almost instantly (it just enqueues a job), so the page's "busy" flag cleared right away even though the real work was still running in the background for minutes. Fixed by exposing `surface_sync.sync_started_at` (the same column the dedup lock above uses) through `/api/connections` as a `syncing` boolean per surface; the connections page now polls every 3s while anything is syncing (stops once nothing is), shows "Syncing…" on the relevant button and in the per-surface status list, and disables that surface's own button without blocking the other one. Verified live: watched `syncing` flip true immediately after triggering a Drive backfill and back to false once it genuinely finished, and directly tested `claimSyncLock`/`releaseSyncLock` in isolation (claim succeeds → second claim while held correctly fails → succeeds again after release).
- ~~Ingestion stored a whole document as a single chunk with no size cap~~ — real fixed-size chunking with overlap now runs at ingest time (`lib/ingest/chunk.ts`), splitting each document into ~1000-char pieces before embedding. This is what previously crashed the HuggingFace reranker (tensor-size mismatch) and blew past Groq's 8,000 TPM limit; `MAX_CHARS_PER_TEXT`/`MAX_CHARS_PER_SOURCE` in `lib/rag/rerank.ts`/`lib/rag/generate.ts` stay in place as safety nets against a pathological chunk, not as the primary truncation mechanism anymore. Re-running this project's own eval suite (`npm run eval`) after the change showed no regression in retrieval accuracy or refusal calibration.
- ~~PDF text extraction isn't implemented yet~~ — implemented via `pdfjs-dist` directly (`lib/ingest/pdf.ts`), wired into both Drive backfill and incremental sync in `lib/ingest/drive.ts`. Verified against this author's own real resume PDFs in Drive: correctly extracted, chunked, and cited in a live query. Required excluding `pdfjs-dist` from Turbopack's server bundle (`serverExternalPackages` in `next.config.ts`) — bundled, its Node worker fallback tries to dynamically import a file Turbopack has relocated and fails at runtime.
- Fixed in passing while rewriting chunk persistence: re-syncing a changed document deleted its old chunk rows from Postgres but never told Qdrant to drop the vectors those rows pointed to, silently leaving orphaned points behind on every edit. `persistChunk` now deletes the stale Qdrant points before writing the new ones.
- ~~Ingestion/backfill runs synchronously in the request cycle~~ — `app/api/ingest/backfill/route.ts` now just validates and publishes a job to Upstash QStash (`lib/qstash.ts`); the real work happens in the signature-verified `app/api/jobs/backfill/route.ts`. The Drive push-webhook receiver (`app/api/webhooks/drive/route.ts`) got the same treatment — it verifies the channel token fast, then enqueues `app/api/jobs/drive-sync/route.ts` to do the actual sync, so a real Google notification gets a fast ack regardless of how much changed. Verified end-to-end against real cloud QStash (not the local dev emulator) via a temporary ngrok tunnel: publish → signature-verified delivery → real ingestion → `surface_sync` updated, and confirmed both job endpoints reject a request with no valid `Upstash-Signature` header (403) before doing any work.
- ~~Nothing registers a Drive `files.watch()`/`changes.watch()` push-notification channel~~ — `lib/google/watch.ts` does, using `changes.watch` (not `files.watch`, which only watches one file's metadata, not the whole change feed). Registration runs automatically at the end of a successful Drive backfill job; a QStash Schedule (`scripts/register-qstash-schedules.mts`, run once against a real deployment) hits a renewal worker (`app/api/jobs/renew-drive-watch/route.ts`) every 6 hours to renew any channel within 2 hours of expiring. Verified end-to-end against real Google infrastructure via a temporary ngrok tunnel: registered a real channel, received Google's own "sync" handshake notification back through the receiver, forced an expiring channel and confirmed the renewal job replaced it with a fresh one, then formally stopped the channel and deleted the schedule when done (both tied to the temporary tunnel, not meant to outlive it). Two things worth knowing, found only by actually testing this rather than trusting docs or memory: omitting `expiration` in the `changes.watch` request silently capped the channel to 1 hour instead of the assumed ~24h — request it explicitly; and despite what's sometimes true for other Google push-notification setups, this did **not** require verifying the webhook domain in Search Console — an arbitrary ngrok address worked with zero domain-ownership proof.
- ~~Gmail ingestion is an interface stub~~ — `lib/ingest/gmail.ts` implements FR-6 (backfill via `messages.list`/`get`) and FR-11 (incremental sync via `history.list` polling, since Gmail push notifications would force a future multi-tenant user through GCP Pub/Sub setup just to connect an inbox). FR-6's opt-in scoping is enforced in code, not just documented: `validateGmailScope` throws rather than defaulting to "index everything" when no label/date range is configured, checked both synchronously at the API route (fast 400) and again inside the job itself. The connections UI (`app/connections/page.tsx`) offers a real label picker (backed by `app/api/ingest/gmail/labels`) plus after/before date inputs. Verified against this author's real, active Gmail inbox end-to-end through a temporary ngrok tunnel: backfilled 211 real messages (label `INBOX`, one week back) with correct subject/from/body extraction (including HTML-to-text fallback for messages with no plain-text part), queried real content and got a correctly cited answer pointing at a real Gmail deep link, then ran the polling worker for real and confirmed it established a genuine `historyId` watermark with zero errors. Chunk counts matched exactly between Postgres and Qdrant (1955/1955) after the run.
- **The eval suite (`tests/eval/`) stayed Drive-only** long after Gmail/Calendar/Sheets ingestion landed, so PRD §5's success criteria were never actually being checked against three of the four real surfaces. Extended `ground-truth.json` from 12 to 23 real cases (Gmail, Calendar, and Sheets questions built from this author's own real ingested content, plus two new real scope-boundary refusal tests — a Gmail question scoped to the Sent folder, a Calendar question outside the backfill window — replacing one stale case that assumed Gmail wasn't ingested yet) and `adversarial.json` from 6 to 7 (a Gmail-specific case per PRD §7's own explicit ask: an injection hidden inside an HTML comment in a forwarded/quoted email body, the highest-risk pattern FR-14 itself names). `seed-adversarial.mts` now reads a per-case `surface` field instead of hardcoding `"drive"`. `report.mts` gained a per-surface breakdown table, since one aggregate number could hide a surface that's actually dragging. Running the extended suite surfaced two real bugs neither of the prior two eval runs (Drive-only) could have caught:
  - **A genuine false refusal on real, correctly-ingested content** ("Who is interviewing me for the Pivotly screening?" scored 0.0482 against the then-0.05 threshold). Checked the real score distribution rather than guessing: genuine out-of-scope refusals scored 0.00037 and 0.0025, while every genuinely answerable case scored at least 0.048 — a real, wide gap. Moved `CONFIDENCE_THRESHOLD` (`lib/rag/pipeline.ts`) to 0.02, ~8x above the highest confirmed-irrelevant score and comfortably below every confirmed-relevant one, rather than resting on the original single-pair estimate.
  - **The generation model silently substitutes typographic Unicode punctuation for plain ASCII inside content it's supposed to reproduce verbatim** — a non-breaking hyphen (U+2011) in a real billing account number, a narrow no-break space (U+202F) between a number and its unit, even inside a person's name ("Keith Rufo"). A real fidelity problem, not cosmetic: a user copying that "identical-looking" account number elsewhere would get a string that doesn't byte-match the original. A system-prompt instruction alone didn't fully close it (kept anyway — it likely helps some of the time), so added `normalizeUnicodePunctuation()` in `lib/rag/generate.ts` to correct it server-side, the same "don't rely on prompt compliance for something enforceable in code" reasoning this file's own citation-marker fallback already uses. Verified live, byte-by-byte: re-queried both previously-broken cases and confirmed plain ASCII (`0x20`, `0x2d`) in the response instead of the Unicode substitutes, then re-ran the full ground-truth suite and confirmed both cases now fully pass with zero regressions elsewhere. Final report: 100% citation accuracy, 100% correct refusals, 100% adversarial resistance across all 4 surfaces; Drive's 63% full-keyword-match rate is the pre-existing baseline (legitimate paraphrasing on 3 questions, unrelated to this pass), not a regression.
- ~~No observability dashboard~~ — `app/observability/page.tsx` + `app/api/observability/route.ts` implement FR-20 (query volume, refusal rate, latency, per-surface sync lag) by aggregating `query_logs` and `surface_sync`, both of which were already being written on every real query/sync since day one — this was a read-only UI on top of existing data, not new instrumentation. Verified against 166 real `query_logs` rows accumulated over this session's own testing: correct totals (166 total / 88 last 24h), a real refusal rate (23%), real latency percentiles (p50 4.2s / p95 13.7s, consistent with what was observed live throughout this session), and correct per-surface lag for all four surfaces.
- **Two real, user-visible bugs existed across every page — Drive, chat, connections, this new dashboard — that no amount of API-level testing all session could have caught, because nobody had actually looked at a rendered page in a real browser until the Claude-in-Chrome extension got connected partway through this pass.** Both fixed and re-verified live in the browser, not just typechecked:
  - **Every page was unreadable in dark mode.** The default Next.js template's `globals.css` flips to a dark background under `prefers-color-scheme: dark`, but every page hardcoded literal `text-black`/`border-black`/`bg-black` Tailwind classes rather than theme-aware tokens — low-opacity black text (labels, timestamps, hints) became nearly invisible against the dark background.
